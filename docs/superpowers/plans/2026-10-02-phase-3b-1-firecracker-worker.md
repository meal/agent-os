# Phase 3b-1: Firecracker Worker and Guest Workspace — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put a Firecracker microVM behind the existing `Worker` trait so that repository code and the verification check run in a guest with no network and nothing of the host but its own drives, with CPU and memory from the contract, the task workspace on a per-task block image that only the guest mounts, `reconcile`/`current_workspace` answered by inspection boots, a reproducible, content-addressed guest image, per-task worker selection, **every Firecracker process jailed through the official `jailer` (chroot, uid/gid drop, cgroup v2 limits, `RLIMIT_FSIZE`, Firecracker's default seccomp) with an explicit `--allow-unjailed` fallback recorded in `Submitted`**, and a KVM-gated test tier whose container is set up so the jailer works — while every 3a guarantee, the crash matrix and the CLI crash demo keep passing, and `docker compose run --rm test cargo test --workspace` stays green without KVM and without root beyond the container's own.

**Architecture:** `agentos-core` gains the shared workspace digest (moved from the engine so host and guest link the same code), the pure patch-parsing rules, and the vsock control protocol (`guest.rs`: messages, limits, frame codec, attempt tokens). A new `agentos-guest` crate (lib + static musl binary) is the guest's PID 1 and agent; its `--fake` mode runs the same request code as a host process on a Unix socket that mimics Firecracker's `CONNECT`/`OK` handshake, so the whole host side is tested without KVM. `agentos-engine` gains `guestlink.rs` (host side of the protocol, `GuestLauncher` seam), `firecracker.rs` (`FirecrackerConfig`, `FirecrackerWorker`, `vm.json` in a host view and a chroot view, preflight, `Inspector`) and `jail.rs` (`JailMode`, the jailer argv, chroot staging by hard links, the root/cgroup probe, the jailed-or-refuse decision, leftover collection — all unit-testable over temp directories, and exercised end to end by a **fake jailer** script that stands in for `jailer_bin`); `SupervisedExecutor` gets a `Reconciler` enum, mints a per-job `attempt_token`, and collects a dead job's jail once the job is settled. The CLI gains `--worker`, `--firecracker`, `--jailer`, `--jail-uid`, `--jail-gid`, `--allow-unjailed`, `image register|list`, records the worker and `jailed` in `Submitted`, and preflights (KVM, binaries, image, jail probe) before touching a task. The jailer is spawned by the worker in the worker's process group and `exec`s Firecracker in place (same pid, pgid, sid, stdio), so every 3a kill path reaches it unchanged. The image recipe, `fetch-firecracker.sh`, `build-guest-image.sh`, the `test-kvm` compose service (with `scripts/kvm-entrypoint.sh` and `scripts/kvm-seccomp.json`) and the KVM tier come last.

## Spec issues found

Each is a place where the spec is ambiguous or contradicts itself; the plan follows the stated resolution rather than silently deviating. **All ten resolutions were accepted by the owner on 2026-10-02** (1, 3 and 4 explicitly; the spec's "Owner decisions" records them).

1. **Protocol failure after `ApplyPatch` was sent: "unresolved" vs "no outcome".** The failure-mapping table says a frame over limit / malformed frame / wrong reply type after the request was sent is an *unresolved* outcome for `ApplyPatch`, while the state machine says every post-send loss (EOF, protocol error, Firecracker exit) is *no outcome, worker exits 1 ⇒ reconciled by inspection*. **Resolution:** the state machine wins for every post-send failure (protocol violation included): the worker writes no outcome and exits 1, the supervisor writes no receipt (3a `fallback_receipt` is `None` for `ReconcileThenRetry`), and `SupervisedExecutor::without_receipt` reconciles through the inspector, which can give a truthful `Applied`/`NotApplied` instead of a blind `unresolved`. Only the `ws.lock`-busy case before anything was sent keeps the spec's explicit *unresolved* outcome for `ApplyPatch` (another VM may be applying the patch; the inspector would also fail on the lock).
2. **A file larger than one raw frame.** Limits say a raw frame is ≤ 16 MiB but one file is ≤ 64 MiB, yet `ReadSnapshot` sends each file as "`File{path, len}` + one raw frame". **Resolution:** a file's bytes follow its `File` message as `ceil(len / RAW_FRAME_LIMIT)` raw frames (every frame full except the last); `len == 0` sends zero raw frames. Both sides use the same `agentos_core::guest::raw_frames_for(len)`.
3. **`--worker` disagreeing with the record.** The spec says `resume`/`cancel`/`revoke`/`status`/`export` build the executor from the recorded worker and "a `--worker` flag that disagrees with the record exits 2", but if the flag defaulted to `host` every later command on a Firecracker task would exit 2. **Resolution:** `--worker` is `Option<WorkerKind>` (env `AGENTOS_WORKER`). Absent ⇒ `submit` uses `host`, every other command uses the recorded worker. Present and different from the record ⇒ exit 2 `task was submitted with worker host`.
4. **How tests reach the fake guest binary.** The spec names `agentos-guest --fake <uds> <root_dir>` and a `GuestLauncher::Fake { guest_bin }`. Cargo only exposes `CARGO_BIN_EXE_<name>` for binaries of the package under test, so engine and CLI integration tests cannot locate a sibling package's binary reliably (and `cargo test -p agentos-engine` would not build it). **Resolution:** `agentos-guest` is a lib + bin crate; `agentos-engine` depends on the lib; the fake guest is reachable as `agentos-guest --fake UDS ROOT`, as `agentos-supervisor fake-guest UDS ROOT` and as `agentos supervise fake-guest UDS ROOT` (the same `agentos_guest::fake::serve`). `GuestLauncher::Fake { program: PathBuf, prefix_args: Vec<String> }` mirrors `SupervisorCmd`; the engine's tests use `CARGO_BIN_EXE_agentos-supervisor`, the CLI uses its own executable. Honoured only with `AGENTOS_TEST_WORKERS=1`.
5. **Where the fake guest keeps the workspace.** The spec says the fake uses `<root_dir>/{workspace,scratch}` directories "instead of block devices" but keeps the `ws.img`-missing checks on the host. **Resolution:** the host side is identical in both modes (it creates `ws.img`/`scratch.img` sparse files, takes `ws.lock`, checks `ws.img` for "missing"); the fake guest is started with `root_dir = <work_root>/<task>` and keeps the workspace in `<root_dir>/workspace/` and the per-boot scratch in `<root_dir>/scratch/` (recreated empty at every fake start, as a VM formats `/dev/vdc` at boot). Tests that need "the workspace is gone" delete `ws.img`; tests that tamper the workspace edit `<root_dir>/workspace/`.
6. **Resource limits and OOM priority for the check without `unsafe`.** The spec sets `RLIMIT_NPROC`, `RLIMIT_NOFILE` and `oom_score_adj` on the check; the obvious `CommandExt::pre_exec` is `unsafe`, which the repo forbids. **Resolution:** the agent re-executes itself as a trampoline, `agentos-guest exec-check --nproc 256 --nofile 1024 --oom 1000 -- PROGRAM ARGS…`, started with std's safe `Command::uid(1001).gid(1001).process_group(0)`; the trampoline calls `rustix::process::setrlimit`, writes `/proc/self/oom_score_adj`, then `CommandExt::exec`s the command (safe; returns only on failure). The agent itself writes `-1000` to its own `oom_score_adj` at boot.
7. **Fake-mode preflight.** The preflight (`/dev/kvm`, `firecracker --version`, image files) cannot pass on a KVM-less host, yet the fake tier must run the CLI end to end. **Resolution:** with `GuestLauncher::Fake` the preflight checks only that the fake program is executable and that the registered image directory parses (`image.json` with `protocol == 1`, named `vmlinux` and `rootfs.squashfs` present, digest matches); tests register a dummy image (three small files). `Submitted.firecracker_version` is `"fake"` in that mode.
8. **Patch-rule sharing between the async engine and the sync guest.** The spec says `ApplyPatch` in the guest validates "as `FixtureExecutor::try_apply_patch`, shared code", but `agentos_engine::patch` is built on `tokio::process`. **Resolution:** the pure parsing (`ALLOWED_SUMMARY`, numstat record parsing, the reason strings `invalid patch: …`, `unsupported patch operation: …`, `binary patches are not supported: …`, `patch touches no files`) moves to `agentos_core::patchrules`; the engine and the guest each run `git` their own way and feed the bytes to the same functions. `symlink_on_path` moves to `agentos_core::workspace` for the same reason.
9. **`Ready.vcpus`.** The spec says "as the guest sees them". **Resolution:** `std::thread::available_parallelism()` in the guest; the KVM tier asserts it equals `worker_vcpus`.
10. **Inspector `vm.json` wording.** "Identical except `workspace` is attached … as well" is read as: the same three drives (`rootfs` read-only, `workspace` = `<work_root>/<task>/ws.img` read-write, `scratch` = `<home>/inspect/<task>/<uuid>/scratch.img`), `uds_path` and `log_path` under the inspect directory, and `--id inspect-<uuid>`.

## Global Constraints

- Use `docker compose` for every build, test and script (`docker compose run --rm test …`; KVM tier `docker compose run --rm test-kvm …`, whose service carries the settings that make the jailer work in a container: `/dev/kvm`, `cap_add: [SYS_ADMIN]`, `security_opt: [seccomp=./scripts/kvm-seccomp.json, apparmor=unconfined]`, `entrypoint: scripts/kvm-entrypoint.sh`; the `test` service does not change). Nothing is installed system-wide: Firecracker and the jailer go to `build/firecracker/v1.17.0/` (git-ignored) or `<home>/bin/`, images to the `guest-images` compose volume or the home registry.
- Check the latest library versions online before pinning and record them (above). `cargo search` only; no request carries the user's email or any identity. The implementer re-runs `cargo search vsock base64 rustix getrandom --limit 1` and `curl -s https://api.github.com/repos/firecracker-microvm/firecracker/releases/latest` before Task 2 and Task 12 and updates the numbers here if they moved.

- The repository has no `unsafe`; `std::env::set_var` is `unsafe` in edition 2024, so test-only environment is passed with `Command::env`/`SupervisedExecutor::with_env`, never set in-process. rustix is the syscall layer (no `libc` calls in our code; the `vsock` crate's internal use is its own). `chown`, `statvfs`, `geteuid` come from rustix (`fs`, `process` features).

The jailed launch path of the worker and the inspector runs end to end in the default tier through a **fake jailer** (`common::fake_jailer`: a `#!/bin/sh` script that parses the documented argv, records it, creates the "cgroup" directory and `exec`s `agentos-supervisor fake-guest` on the chroot's socket). The real `probe` is asserted per environment: non-root ⇒ `needs root`; root with a read-only cgroup tree (the `test` service) ⇒ `read-only`; `test-kvm` ⇒ `Ok`. No test of the default tier writes to `/sys/fs/cgroup`.

- Flakiness control: the supervisor, supervised, firecracker, jail and crash-matrix suites run 20× in one container before their task is done; the KVM tier 10×; kill tests use leases of hundreds of milliseconds with real clocks.

## Review Focus

An adversarial reviewer should attack these; each line names the test that pins it in the owning task.

- **A VM that survives supervisor death.** SIGKILL the supervisor mid-job: the worker and the Firecracker (or fake guest) process must die by the controller's fence, and the guest must also shut itself down on connection EOF within 500 ms. Tests: `supervisor_sigkill_then_fence_leaves_no_worker_and_no_guest_process` (Task 8), `fake_guest_shuts_down_within_500ms_of_eof` (Task 4), `vm_dies_with_the_worker_on_lease_expiry` (Task 13).
- **Workspace inspectability after a dead VM.** Kill the VM right after `ApplyPatch` was sent: the image holds the base or the base plus the patch, never a torn tree, and inspection says which. Tests: `patch_killed_after_request_is_reconciled_by_inspection_not_failed` (Task 7), `inspection_after_a_killed_patch_vm_converges_to_succeeded` (Task 13), `reconcile_trichotomy_on_base_patched_and_tampered_workspace` (Task 7).
- **Digest compatibility.** The guest and host must produce the same digest for the same tree, else every `WorkspaceUpdated` would disagree with the host's `check_inputs`. Tests: `golden_fixture_digests_are_unchanged` (Task 1), `snapshot_digest_from_the_guest_equals_the_host_digest` (Task 8, Task 13).
- **Frame-size DoS.** A guest (or a stray peer) announcing a 4 GiB frame must not make the host allocate; an oversized or malformed frame is a protocol failure, never a hang. Tests: `decode_rejects_a_length_over_the_limit_without_allocating` (Task 2), `a_frame_over_the_limit_is_a_protocol_failure` (Task 5), `a_reply_that_never_comes_is_bounded_by_the_lease` (Task 8).
- **Guest-controlled strings reaching host paths or logs.** `SnapshotDone.files`, `PatchApplied.paths`, `Refused.reason`, `Verified.stdout` are data: they are placed into JSON outputs only, never joined onto a host path, never written to the console/log unescaped, bounded by the JSON frame limit. Tests: `guest_paths_in_replies_never_touch_host_paths` (Task 5), `a_refused_reason_is_copied_verbatim_into_the_failure_outcome_and_bounded` (Task 5).
- **Token and handle leakage.** No capability handle is in `request.json`'s worker config, `vm.json`, the kernel command line, `console.log`, `firecracker.log`, `stderr.log`, the jailer argv, or any frame; the token appears only in `request.json` and `Hello`. Tests: `no_handle_and_no_token_appears_in_vm_json_console_or_firecracker_log` (Task 5), `attempt_token_is_minted_fresh_per_job_and_never_logged` (Task 7), `fake_jailer_records_the_argv_the_worker_passes` (Task 6: the argv holds no token).
- **Reconcile trichotomy correctness.** `NotApplied` only when the digest equals the base; `Applied` only when reversing the patch gives the base back; everything else `Unknown` with the 3a reason text; `Unknown` on a busy `ws.lock`, a missing image, a boot failure, or a timeout. Tests: `reconcile_trichotomy_on_base_patched_and_tampered_workspace`, `inspection_failure_is_unknown_never_not_applied` (Task 7).
- **Image tampering between registration and boot.** A byte changed in a registered image after `submit` must fail the preflight before the task is touched (and the worker's own re-digest before every launch must refuse it). Tests: `a_tampered_registered_image_fails_the_preflight_before_the_task_is_touched` (Task 10), `the_worker_refuses_to_launch_when_the_image_digest_moved` (Task 5).
- **Chroot escape and the hard links.** The chroot must contain exactly the documented files before the jailer runs; `vm.json` inside it references chroot-relative paths only; hard links expose inodes, not paths, and the registry files are root-owned `0444`, so a compromised jailed process can read but never alter the registry, the journal, `request.json` or another task's image. Tests: `stage_links_only_the_documented_files_and_nothing_else`, `registry_files_stay_root_owned_and_read_only_after_staging`, `chroot_view_is_the_golden_jailed_vm_json` (Task 6), `jailed_firecracker_runs_as_the_jail_uid_in_its_chroot_and_cgroup` (Task 13).
- **Hard link vs copy of the image.** Staging never copies: `EXDEV` is a clear failure naming both paths, and the preflight refuses a home that spans filesystems before the task is touched. Tests: `stage_reports_exdev_with_both_paths` (Task 6), `probe_with_reports_the_first_failing_step_in_order` (Task 6, the "different filesystems" row), `submit_refuses_when_the_jailer_is_unavailable_and_the_task_is_untouched` (Task 10).
- **Leftover chroot and cgroup after SIGKILL.** A job killed by the supervisor or the fence leaves an empty cgroup and a chroot with hard links (keeping `scratch.img` blocks alive); the controller must collect them once — and only once — the job is settled; a dead inspector's directory must be collected by the next inspector.
